The solution · GenUI

The model decides what to show. Your app decides how it looks.

Generative UI: an LLM puts together an interface at runtime, for this user, for this context, from components you built and own.

What it isn't

Four common misconceptions.

NOT

Code generation

The model never writes Flutter or React. It picks from components you already ship.

NOT

A design tool

Figma and Pencil generate designs for your team. GenUI generates UI for your users, live.

NOT

A predefined flow

There's no fixed script. The next screen depends on who's asking and what they just did.

NOT

Your whole app

Build the core flows by hand. Generate the long tail.

Protocols

A protocol is just the format the model writes.

OUR BASELINE

A2UI

Google's open protocol. JSON messages with a flat list of components. Built to stream.

ALTERNATIVE

OpenUI Lang

Thesys's open format. Compact, code-like lines that use fewer tokens than JSON.

Different syntax, same idea: describe the UI, and your client renders it with its own components.

A2UI

It's just JSON.

A flat list of components. Each one has an id, a type, and props.

  1. id so it can be referenced later
  2. component is a name from your catalog
  3. children point at ids, not nested objects

The catalog

The catalog is the allowlist for the LLM.

The model can only choose what's on it.

NAME

What the model calls it.

SCHEMA

name, route, days, price

What the model has to send.

BUILDER

Your component

What the user actually sees.

Not in the catalog? It can't render.
Component builders

A schema plus a builder.

The schema tells the model what to send. The builder turns it into your component.

Your app
final cruiseCard = CatalogItem(
  name: 'CruiseCard',
  dataSchema: S.object(
    properties: {
      'name': S.string(),
      'route': S.string(),
      'days': S.integer(),
      'price': S.number(),
    },
    required: ['name', 'route', 'days', 'price'],
  ),
  widgetBuilder: (ctx) {
    // A widget from your design system
    return CruiseCard(
      name: ctx.data['name'],
      route: ctx.data['route'],
      days: ctx.data['days'],
      price: ctx.data['price'],
    );
  },
);
A better schema

Send IDs, not data.

The model picks the cruise. Your app loads the facts.

  1. Accurate. Prices come directly from your API, not through the model.
  2. Fresh. A price change shows up without asking the model again.
  3. Checkable. A bad ID fails loudly. A wrong price doesn't.
  4. Cheaper. One short ID instead of every field.
Before · the model retypes your data
{ "id": "alaska", "component": "CruiseCard",
  "name": "Alaska", "days": 7, "price": 1249,
  "route": "Seattle → Juneau → Skagway" }
After · the model picks, the app loads
{ "id": "alaska", "component": "CruiseCard",
  "cruiseId": "AK-0612" }
Your builder
dataSchema: S.object(
  properties: {'cruiseId': S.string()},
),
widgetBuilder: (ctx) {
  // Route, days, and price from your API
  return CruiseCard.load(ctx.data['cruiseId']);
},

Actions

Actions send data back.

Bound paths become real values before they leave the device. The agent replies with new UI.

Tool calling

Real data, not made-up data.

  1. The user asks for a summer cruise under $2,000
  2. The model calls searchCruises
  3. Your server returns real cruise IDs
  4. The model shows each one as a CruiseCard

A2UI also has client-side functions like formatCurrency and required. They format and validate in the renderer, without a round trip.

Your server · tool definition

  "name": "searchCruises",
  "description": "Find cruises by region, month, and max price",
  "parameters": {
    "type": "object",
    "properties": {

      "month":    { "type": "string" },

What's still hard

A great demo isn't a production app.

HALLUCINATIONS

Wrong facts, broken layouts, wrong answers

Send IDs, validate against the catalog, retry on errors.

SAFETY

Bad asks in, bad offers out

Screen every turn, in and out, with a policy layer like Model Armor.

COST

A screen can use ~10× the tokens of a text reply

Measure every render. Cache and route to smaller models.

LATENCY

A full screen with tool calls can take a minute

Stream as it renders. Generate small zones, not whole pages.

TESTING

"It rendered" doesn't mean "it answered"

Evals that score structure and intent, not just parsing.
